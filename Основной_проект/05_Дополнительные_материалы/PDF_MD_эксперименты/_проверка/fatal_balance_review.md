# Fail-fast при недоступности DeepSeek

Проверка 16.11.2026. Изменены только `tools/run_deepseek_corpus.py`, `tools/monitor_run.py`, `tools/test_deepseek_fatal.py` и эта записка. Контроллеры, модели и платные запросы не запускались; восстановление после пополнения не выполнялось.

## Подтверждённые факты и границы проверки

- В реальном `_проверка/job.json` прочитаны `status=blocked_deepseek_balance` и `failure=HTTP402 insufficient_balance_error`. Этот файл и живой controller JSON не переписывались данным агентом
- По переданному root результату `/user/balance`: `is_available=false`, `total_balance=USD -0.03`. Повторной проверки API в этой задаче не было
- Причина предыдущих native-crash (`fz_load_jpx`, небезопасный совместный PyMuPDF) сообщена root. Патч не меняет архитектуру исправления: PDF готовятся в spawned ProcessPool, API — в ThreadPool. Крэши здесь не воспроизводились

## Исправлено

1. Общий thread-safe stop для всей очереди. HTTP 401/402/403 и явная ошибка исчерпанного баланса/квоты блокируют всю очередь. Ошибка получения credentials также не повторяется на каждой странице
2. Stop проверяется перед каждой попыткой и повтором, backoff прерывается событием. Не начатые futures отменяются. Отложенные страницы и отчёты имеют `deferred_external_dependency`, не `source_error` и не новые page failures
3. Успех, уже находившийся в работе, учитывается как успех. Сохранённые parsed/raw не удаляются. Уже сохранённые ответы отдельно учтены и не включаются в список отложенных номеров при blocked-снимке
4. Local preflight по сохранённым job/controller metadata выполняется до пулов, подготовки PDF и API. При blocked возвращается exit 3; вызова `/user/balance` нет. Прямой вход `attempt_page` также защищён от обхода сохранённого blocked
5. Fatal dependency сохраняется; автоматической разблокировки нет. Сам факт пополнения счёта не запускает обработку: требуется отдельное явное решение оператора и снятие сохранённой блокировки
6. Monitor завершает по свежему job. Если он blocked, сохраняет status и failure, добавляет только `monitor_ended_at`; успешный Codex не превращает DeepSeek в ended. Подменённый PID старый monitor не перезаписывает

Уже отправленные параллельные запросы невозможно отозвать этим Python-stop. Он останавливает новые элементы и повторы; ответы уже выполняющихся запросов сохраняются. Не обещается, что при 64 API-слотах после первого ответа 402 вообще не останется других ранее отправленных запросов.

## Проверки

Команда без внешних сервисов:

```bash
python3 -W error::ResourceWarning -m unittest discover -s tools -p test_deepseek_fatal.py -v
```

**10/10 тестов прошли.** Модули провайдера, подготовки PDF и транскрипции подменены mock при импорте; Keychain, native PDF, API и subprocess моделей не вызываются.

- По 14 731 элементу через shared stop для каждого 401/402/403: ровно один mock-вызов до блокировки, ни одного повтора
- Реальный event-loop на 480 элементах двух отчётов, API worker 1: один mock-успех и один mock-402, всего 2 вызова, затем cancel/deferred;0 page failures и0 source errors
- Сохранённый blocked до старта:0 пулов и 0 вызовов транскрипции; очередь отражена как внешняя зависимость
- Parsed/raw и успех in-flight сохранены; существующий успешный ответ исключён из deferred-номеров
- Monitor сохраняет blocked при `overall_complete=true` от другого результата и не переписывает job с новым PID
- Лок-файл корректно закрывается, включая SystemExit

Это проверенный патч и mock-верификация. Реальная очередь не перезапускалась, текущие live JSON не выдаются за заново собранные этим кодом.
