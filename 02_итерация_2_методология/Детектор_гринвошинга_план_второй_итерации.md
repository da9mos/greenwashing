## Методология: что такое риск гринвошинга

Рабочее определение для проекта: риск гринвошинга — это наблюдаемый
разрыв между ESG-заявлением и тем, что подтверждают показатели самого
отчёта и внешние события. Мы измеряем разрыв, а не умысел: результат —
риск-сигнал для внутренней аналитики, не обвинение.

### Три типа заявлений

| Тип           | Признак                                         | Пример                                              | Чем проверяем                                                            |
|---------------|-------------------------------------------------|-----------------------------------------------------|--------------------------------------------------------------------------|
| Обязательство | Будущее время + цель (цифра, срок, базовый год) | «Снизим выбросы на 30% к 2030 г. от уровня 2019 г.» | Динамика показателя и судьба цели в следующем отчёте                     |
| Результат     | Прошедшее время + измеримый эффект              | «Сократили сбросы загрязнённых вод на 12%»          | Таблицы показателей отчёта, штрафы, инциденты за тот же период           |
| Декларация    | Нет измеримого содержания, ценностные слова     | «Мы бережно относимся к природе»                    | Не проверяется цифрами; противоречит фактам, если есть инциденты по теме |

### Три класса и правила

- **Подтверждено**: есть опорный факт (цифра в таблице отчёта, внешний
  источник), совпадающий по направлению и порядку величины, и нет
  противоречащих.

- **Декларативно**: проверить нечем — нет измеримого содержания или нет
  данных (аналог not enough info).

- **Противоречит фактам**: показатель движется в обратную сторону, цель
  тихо убрана или сдвинута, есть штраф, предписание, суд или авария по
  той же теме и периоду.

Предлагаем согласовать с заказчиком, что «декларативно» включает оба
случая, а причину пишем в отдельное поле (нет цифры / нет данных / срок
не наступил). Так сохраняем три класса из ТЗ и не смешиваем «пустое
заявление» с «не нашли данных».

### Флаги риска (для кодбука и индекса)

- Цель из прошлогоднего отчёта исчезла или перенесена без объяснения.

- Смена базового года, единицы или периметра отчётности.

- Успех показан только в удельных показателях, абсолютные растут.

- Штраф, предписание, иск, авария или несчастный случай по теме, которую
  отчёт называет успехом.

- Нет независимого заверения нефинансовой отчётности.

### Черновик индекса (считаем в итерации 3, формулу фиксируем сейчас)

GRI_c = w_1 \cdot \frac{N^{contr}\_c}{N_c} + w_2 \cdot
\frac{N^{decl}\_c}{N_c} + w_3 \cdot \frac{N^{unmet}\_c}{N^{commit}\_c} +
w_4 \cdot \min\left(1, \frac{S^{ext}\_c}{S\_{max}}\right)

Здесь доли противоречащих заявлений, деклараций и невыполненных
обязательств, а S — взвешенная по тяжести сумма внешних фактов за
период. Веса w подбираем экспертно и проверяем чувствительность рангов к
их изменению.

## Извлечение заявлений LLM

Пайплайн итерации: PDF → текст по страницам → чанки по 1–2 тыс. символов
с номером страницы → фильтр по ESG-лексике (E, S и G) → LLM возвращает
JSON-список заявлений → таблица claims.

Правила промпта:

- Одно заявление = одна проверяемая мысль; составные фразы делим.

- Текст цитируем дословно (защита от галлюцинаций: скрипт проверяет, что
  цитата есть в чанке).

- Не берём описания законов, методик, благодарности и факты без оценки
  компании.

- Few-shot: 6–9 примеров из кодбука, по два-три на тип, включая
  пограничные.

- Фиксируем модель, версию и temperature = 0, чтобы куратор воспроизвёл
  результат.

Поля таблицы claims (сразу в формате итогового датасета из ТЗ):

| Поле                                        | Пример                                                                                                                                                               | Кто заполняет   |
|---------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------|
| claim_id                                    | NORN-2024-017                                                                                                                                                        | скрипт          |
| company_id, year, report, page              | NORN, 2024, ОУР, с. 112                                                                                                                                              | скрипт          |
| text                                        | дословная цитата                                                                                                                                                     | LLM             |
| type                                        | обязательство / результат / декларация                                                                                                                               | LLM             |

| metric, value, unit, base_year, target_year | выбросы SO2, −30, %, 2019, 2030                                                                                                                                      | LLM             |

## Шаблон базы фактов

База фактов — это две таблицы, которые связаны с заявлениями одними
ключами (company_id, year, topic): внутренняя динамика из отчётов и
внешние события. Без общих ключей в итерации 3 сопоставление придётся
делать вручную.

### Таблица metrics_dynamics («заявление прошлого года → результат текущего»)

| Поле                                          | Что пишем                                                                                       |
|-----------------------------------------------|-------------------------------------------------------------------------------------------------|
| company_id, topic, metric, unit               | ключи и показатель (выбросы ЗВ в атмосферу, тыс. т)                                             |
| claim_id_commitment                           | ссылка на обязательство в claims                                                                |
| target_value, base_year, target_year          | цель, как сформулирована в год N                                                                |
| value_2023, value_2024, value_2025 + страница | факт из таблиц каждого отчёта                                                                   |
| restated                                      | был ли пересчёт прошлых значений, смена периметра                                               |

Статусы «на траектории / отстаёт» нужны, потому что срок большинства
целей (2030) ещё не наступил: прогресс сравниваем с линейной траекторией
от базового года к целевому.

    11.11 пример «заявление → динамика → внешний факт», заготовка кейса
    для критерия 7.

4.  **Общие ключи таблиц.** Шаблоны Никиты и Егора К. делаются
    независимо. Договоритесь сразу об одном словаре: company_id, year,
    topic, claim_id (см. разделы выше), и ведите всё в одной таблице с
    вкладками claims / metrics_dynamics / external_facts.

5.  **Классы и блок E/S/G никому не назначены.** Критерии 2 и 5 требуют
    тип, блок и класс (подтверждено / декларативно / противоречит).
    Классифиция — итерация 3, но определения классов лучше записать
    сейчас у Егора Д. (рядом с индикаторами), а поле «блок + тема»
    добавить в инструкцию Григория и промпт Георгия.

6.  **Квоты с запасом и по типам.** 500 / 30 ≈ 17 верно, но LLM лучше
    извлечь 700–800, чтобы после чистки осталось 500+. Квоту стоит
    задать и по типам (ориентир: 40% обязательств, 35% результатов, 25%
    деклараций) и по годам, иначе не хватит пар «обязательство 2023 →
    результат 2024–2025».
