# Конвейер без API-ключа: как работает детектор

*Версия от 12.11.2026. Решение Григория: ключ `ANTHROPIC_API_KEY` не заводим и за API отдельно не платим. Этот файл главнее всех мест в старых документах, где говорится о ключе, `temperature = 0`, кэше ответов API и запуске модели из скриптов.*

## 1. Коротко

- **Ключ не нужен.** Ни один скрипт не обращается к модели.
- **Всё, где нужно понимать текст** (найти заявления, выписать цели, разметить эталон, поставить класс), делает Claude в потоках проекта «Сбер гринвошинг» на claude.ai. Работа идёт **партиями**: скрипт готовит файл партии, поток читает промпт и партию и записывает ответ в файл.
- **Всё механическое** (разбор PDF, нарезка на куски, отбор кусков, проверка цитат, сборка таблиц, расчёт динамики, каппы, F1, индекса) делают скрипты Python без модели. Их может запустить кто угодно, без подписки и ключа.
- **Цена:** только подписка Claude. Ограничения: лимиты подписки и время. Вместо одного ночного прогона будет порядка 50–60 потоков за несколько недель.
- **Воспроизводимость** держится не на `temperature = 0`, а на сохранённых ответах модели и журнале партий: все таблицы заново собираются из этих ответов одной командой.

## 2. Где раньше был нужен ключ и что стало

| Место | Как было задумано | Как теперь |
|---|---|---|
| Старт у Григория (`Задачи_команды`, README) | Ключ в переменных среды Windows, перезапуск приложения | Не нужен. Для старта остаются «скачивай» и текст замечания заказчика |
| Поиск заявлений, `extract.py` (Георгий) | Скрипт вызывает модель по каждому куску | Скрипт готовит партии, Claude в потоке пишет ответы в `llm/extract/`, скрипт проверяет цитаты и собирает `claims.csv` |
| Цели ≤2025 и «Динамика» (Никита) | Модель через API читает таблицы показателей | Те же партии в потоках; статусы, пересчёты и флаги считает скрипт `dynamics.py` без модели |
| Второй разметчик (Егор Д., критерий 4) | Вторая модель через API с другим промптом | Отдельный поток на другой модели Claude с промптом B, не видит ответов A (раздел 6) |
| Классификация, `classify.py` | Три прогона при `temperature = 0` | Два независимых прохода в разных потоках; расхождение → третий проход, затем Егор Д. |
| `config.yaml`: модель и `temperature = 0` | Фиксируются параметры вызова API | Фиксируются версии промптов, размеры кусков и партий, квоты; модель записывается в журнал по каждой партии |
| `cache/` с ответами API | Повторный запуск не тратит деньги | `llm/` с ответами потоков, по файлу на партию; файлы не перезаписываются |
| `run.py --stage all` | Одна команда делает всё, включая вызовы модели | `run.py` делает только механические шаги и собирает таблицы из готовых ответов в `llm/` |
| Внешние факты (Егор К.) | Поиск в чатах Claude и вручную | Без изменений: веб-поиск в потоках, сайты с капчей или российским IP через встроенный браузер на компьютере Григория |
| Таблица определений (Егор Д.) | В чате Claude с поиском | Без изменений |

Кода в проекте ещё нет, поэтому переписывать ничего не пришлось: ключ упоминался только в документах. Они обновлены (список в разделе 10).

## 3. Схема

```
скрипты (без модели)                        потоки проекта (Claude)                 скрипты (без модели)
PDF → страницы → куски → отбор → партии ──► промпт + партия → ответ JSON ──► проверка → таблица
data/reports  data/pages  data/chunks  batches/<этап>/   prompts/       llm/<этап>/<версия>/   check.py   data/out/
                                                                                    └──► runs/manifest.csv (журнал)
```

Этапы, на которых работает модель, и что идёт на вход:

| Этап | Вход партии | Ответ модели | Что делает скрипт после |
|---|---|---|---|
| `extract` — заявления | ≤20 кусков из одного отчёта | список заявлений: цитата, страница, тип, блок, тема, цифры | проверка цитаты, номера `claim_id`, `claims.csv` |
| `targets` — цели ≤2025 | ESG-куски отчёта 2023 года с целями | цели с базой, значением и сроком | `targets.csv` |
| `dynamics` — показатели | страницы с таблицами показателей за 3 года | значения по годам со страницами | статусы целей, пересчёты, «удельные против абсолютных» в `metrics_dynamics.csv` |
| `annotate_A`, `annotate_B` — эталон | 25 заявлений с доказательствами, без чужих ответов | тип и класс с обоснованием | каппа, список расхождений для Егора Д. |
| `classify` — классы | 25 заявлений с их доказательствами | класс, ссылка на `fact_id` или страницу, обоснование | проверка ссылки, слияние двух проходов, `classes.csv` |

## 4. Партии

- **Единица работы — партия.** Для извлечения это до 20 кусков по 1 500 знаков (около 30 тыс. знаков) из одного отчёта. Для разметки и классификации 25 заявлений.
- **Отбор кусков до модели.** Скрипт оценивает каждый кусок по словарю ESG-слов и берёт лучшие 60 кусков отчёта с квотой не меньше 15 на каждый блок E, S, G. Это 3 партии на отчёт. Модель не читает весь отчёт целиком, поэтому полноту поиска честно меряем на эталоне (как и раньше).
- **Имя партии постоянное:** `batches/extract/NORN-2024-ОУР_b01.jsonl`, ответ к ней `llm/extract/v1/NORN-2024-ОУР_b01.json`. Строка партии: `chunk_id; report_id; page; text`.
- **Один поток — одна компания на одном этапе** (для NORN это 9 партий извлечения). Длинные потоки не делаем: к концу длинного разговора внимание модели хуже, и в контексте копятся чужие ответы.
- **Кто запускает.** Григорий пишет в чат проекта, например: «запусти извлечение по NORN, MAGN, CHMF». Координатор открывает по потоку на компанию со стандартной инструкцией (приложение А). Одновременно 3–5 потоков, чтобы не упереться в лимиты.
- **Если поток оборвался** (лимит, ошибка), ничего не теряется: в журнале видно, какие партии готовы, новый поток продолжает с первой незаконченной.

**Порядок объёма** (оценка, уточним после разбора PDF): извлечение около 280 партий (92 отчёта × 3), цели и динамика около 120, эталон A и B около 16, классификация два прохода около 60. Итого около 500 партий, при 9–10 партиях на поток это 50–60 потоков.

## 5. Где хранятся результаты

- **Главная копия — библиотека проекта**, папка `03_итерация_3_пайплайн/`. Её видят все потоки проекта, и она не пропадает, когда поток закрывается.
- **Копия на компьютере Григория:** `C:\Users\User\Desktop\Гринвошинг\03_итерация_3_пайплайн\`. Обновляется после каждого этапа. Это резервная копия и папка, из которой позже сделаем репозиторий.
- **PDF-отчёты** лежат в обоих местах. Если в библиотеке не хватит места, PDF остаются только на компьютере, а в библиотеке хранится текст по страницам (`data/pages/`): потокам нужен только он.

```
03_итерация_3_пайплайн/
  README.md
  config.yaml            версии промптов по этапам, размер куска и партии, квоты, порог проверки цитаты
  data/reports/          PDF (после «скачивай»)
  data/pages/            текст по страницам: код_отчёта.jsonl
  data/chunks/           куски с номером страницы
  batches/<этап>/        входные партии для потоков
  prompts/               промпты с версией: extract_v1.md, targets_v1.md, dynamics_v1.md,
                         annotate_A_v1.md, annotate_B_v1.md, classify_v1.md
  llm/<этап>/<версия>/   ответы модели, по файлу на партию (не перезаписываются)
  runs/manifest.csv      журнал партий
  data/out/              claims.csv, targets.csv, metrics_dynamics.csv, external_facts.csv,
                         gold.csv, classes.csv, index.csv
  src/                   parse.py, chunk.py, make_batches.py, check.py, merge.py,
                         dynamics.py, agreement.py, metrics.py, index.py
  run.py                 python run.py --company NORN  (только механика, из готовых ответов)
  requirements.txt
```

**Журнал партий `runs/manifest.csv`** (CSV, `;`, UTF-8 с BOM):

`batch_id; stage; company_id; report_id; input_file; input_sha256; prompt_file; prompt_sha256; model; thread; started_at; finished_at; status (готово / ошибка формата / переделать); n_items; n_rejected; checked_by`

Хэш `sha256` доказывает, что ответ получен именно на эту партию и именно по этой версии промпта. Модель поток записывает ту, на которой реально работал.

## 6. Как обеспечить качество разметки

1. **Промпт в файле с версией.** Поток читает только файл промпта и свою партию. Промпт не пересказывается своими словами и не правится внутри потока. Few-shot: 6–9 примеров из кодбука, включая пограничные.
2. **Строгий формат ответа.** JSON по схеме из промпта. `check.py` отбрасывает строку без обязательного поля, с чужим `chunk_id`, с типом или классом не из списка. Ошибку формата поток исправляет сам, содержание не трогает.
3. **Цитата дословно.** Цитата сверяется с текстом куска (rapidfuzz, совпадение ≥ 95). Не совпала — строка выбрасывается и считается в `n_rejected`. Если в партии выброшено больше 10%, партию переделывают в новом потоке.
4. **Класс только со ссылкой.** Классификатор видит заявление и только найденные доказательства и обязан сослаться на `fact_id` или страницу из входа. `check.py` проверяет, что ссылка действительно была во входе; нет ссылки — «декларативно».
5. **Два прохода классификации** в разных потоках. Совпали — класс принят. Не совпали — третий проход, затем пометка «на проверку» для Егора Д. Доля совпадений первых двух проходов идёт в отчёт как мера устойчивости.
6. **Независимые разметчики эталона.**
   - A и B работают в разных потоках, по разным промптам (`annotate_A_v1.md`, `annotate_B_v1.md`).
   - Поток B переключается на другую модель Claude (например, A на Opus, B на Sonnet).
   - B получает заявления в другом порядке и не имеет доступа к ответам A: ответы лежат в разных папках, инструкция запрещает открывать чужую, а соединяет их только `agreement.py` после того, как оба закончили.
   - В отчёте пишем честно: оба разметчика — модели семейства Claude, независимость обеспечена процедурой, спорное решал человек.
7. **Пилот перед массовым прогоном.** Каждый новый промпт сначала идёт на одной компании (NORN). Владелец этапа проверяет 20 строк по PDF, и только потом промпт идёт на остальные компании.
8. **Отложенная часть эталона** (40 заявлений) не используется при доработке промптов, на ней меряем итоговое качество.
9. **Выборочная проверка людьми** — как в «Задачах команды»: каждый владелец сверяет свои 5–10 строк с первоисточником и отмечает это в столбце `checked_by` журнала.

## 7. Воспроизводимость (критерий 9)

Без API нельзя задать `temperature = 0` и повторить тот же вызов. Поэтому воспроизводимость делим на два уровня и честно пишем об этом в отчёте.

- **Уровень 1, полный.** `python run.py --company NORN` (или `--all`) собирает все таблицы из сохранённых ответов в `llm/` без модели и без ключа. Результат совпадает с `data/out/` байт в байт. Именно это проверяет куратор.
- **Уровень 2, повтор модели.** Любую партию можно заново прогнать в новом потоке по тому же промпту. Ожидаем не тот же текст, а близкий результат. Меряем: повторно прогоняем по одной партии извлечения на компанию (около 10%) и весь эталон на этапе классификации, считаем долю совпадений и каппу «прогон — повтор». Это число идёт в отчёт.
- **Правила:** ответы руками не правятся; новый промпт — новая версия и новая папка `llm/<этап>/v2/`; старые версии не удаляются.

## 8. Порядок запуска (после «скачивай»)

1. Скачивание 92 файлов через встроенный браузер на компьютере Григория (ключ для этого не нужен и не был нужен).
2. Скрипты: разбор PDF, куски, отбор, партии; отчёт о качестве текста (какие отчёты читаются плохо).
3. Промпты v1 по кодбуку; пилот на NORN по каждому этапу, проверка владельцем.
4. Девять первых компаний (NORN, MAGN, CHMF, LKOH, TATN, PHOR, SIBR, SGZH, RVDK) — контрольная точка 8-й недели. Затем остальные 21.
5. Параллельно: цели и динамика (Никита), внешние факты (Егор К.).
6. Эталон A и B → каппа → разбор расхождений → классификация двумя проходами → индекс.

## 9. Готовый текст для отчёта (раздел «Методика» и «Ограничения»)

> Ответы языковой модели получены в интерфейсе Claude (проект claude.ai), а не через программный API, поэтому параметры генерации (температура) не фиксировались. Воспроизводимость обеспечена так: все входные партии, версии промптов и ответы модели сохранены с контрольными суммами, а все таблицы и метрики пересчитываются из них детерминированными скриптами. Устойчивость самой модели оценена повторным прогоном части партий: доля совпадений составила … Второй разметчик эталона — другая модель того же семейства с другой инструкцией, работавшая независимо; расхождения разобраны человеком.

## Приложение А. Стандартная инструкция для потока

Координатор вставляет её при открытии потока, подставив этап, компанию и версию промпта.

```
Этап: extract. Компания: NORN. Промпт: 03_итерация_3_пайплайн/prompts/extract_v1.md.
1. Прочитай промпт целиком. Не пересказывай и не меняй его.
2. Возьми из runs/manifest.csv партии этой компании и этапа со статусом не «готово»,
   по порядку. Партии лежат в batches/extract/.
3. На каждую партию: прочитай её, ответь строго в формате JSON из промпта,
   запиши ответ в llm/extract/v1/<имя партии>.json. Существующие файлы не перезаписывай.
4. Запусти python src/check.py на этот ответ. Ошибку формата исправь, содержание не меняй.
   Если выброшено больше 10% строк, поставь статус «переделать» и переходи к следующей.
5. Допиши строку в runs/manifest.csv: хэши, модель, на которой ты работаешь, время, статус, n_items, n_rejected.
6. Не открывай ответы других компаний, других этапов и другого разметчика.
7. В конце: сколько партий готово, сколько строк, сколько выброшено, что требует внимания.
Ничего не скачивай и не выдумывай: цитата только дословно из партии, со страницей.
```
